# Performance and large transfers

Every number here was measured on the hardware named beside it. None of it is a
claim about your machine — rerun `tests/load/benchmark.py` on the host you care
about. Payload is generated on the fly and never stored, so no measurement
touches the disk.

## Design constraints

The hot path is C, libuv and OpenSSL end to end. Python is never in the payload
path unless a message handler is explicitly enabled. Backpressure pauses the
upstream read at a 256 KiB high watermark and resumes below 128 KiB, so a slow
receiver stalls its producer rather than growing the broker. UDP cannot push
back that way, so it uses bounded queues with an explicit drop policy instead.

## Benchmark

```bash
tests/load/benchmark.py --bytes 512MiB
tests/load/benchmark.py --modes direct,open-tcp --json results.json
```

It compares direct localhost against the tunnel modes and reports throughput,
connection rate, latency, CPU and peak RSS.

### Measured — VPS, 512 MiB per run, loopback

| Mode | MiB/s | vs direct | conns/s | p50 latency | CPU s | peak RSS |
|---|---:|---:|---:|---:|---:|---:|
| direct localhost | 1993.9 | 100% | 4599.9 | 0.024 ms | — | — |
| open TCP tunnel | 787.8 | 39.5% | 680.3 | 0.081 ms | 0.90 | 10.1 MB |
| closed TCP tunnel | 534.0 | 26.8% | 368.7 | 0.114 ms | 1.11 | 11.0 MB |
| open TCP + Python handler | 635.4 | 31.9% | — | — | 1.28 | 9.8 MB |
| open UDP tunnel | 160.7 | 8.1% | — | 0.080 ms | 3.16 | 11.8 MB |

Reading these honestly:

- **Two TLS hops cost roughly 60%** of raw loopback throughput. Every byte is
  encrypted twice (client↔broker is plaintext for open mode, broker↔agent is
  TLS) and crosses two extra processes. On a real network the link is usually
  the limit long before this is.
- **Closed mode is slower than open mode** because the consumer side is also
  TLS, so there are three encrypted legs rather than two.
- **UDP costs more CPU per byte** than TCP: each datagram is its own DTLS
  record with its own syscall, where TCP amortises over 16 KiB records. UDP
  throughput here is packets-per-second bound, not bandwidth bound.
- **The Python handler path** is the full topology (broker → C agent → local
  Python proxy → service). It is close to open TCP at this payload size because
  the identity handler is cheap; a handler doing real work will be much slower.
  Leave handlers disabled for bulk transfer.

### Connection setup

Connection rate is a separate axis from throughput, because each new stream
costs the agent a fresh TLS data connection to the broker. Measured on dev:

| | before TCP_NODELAY | after |
|---|---:|---:|
| open TCP | 21 conns/s | 741 conns/s |
| closed TCP | 19 conns/s | 412 conns/s |

Nagle interacting with the peer's delayed ACK was adding ~40 ms to every small
request/response; disabling it on all relay sockets removed that. Setup is now
~1.4 ms per connection on loopback, dominated by the TLS handshake.

Pre-established worker connections would cut this further and the protocol
leaves room for them, but they are not in v1 — see
[ADR-0001](adr/0001-tcp-transport.md).

## Large transfers

The requirement is at least 5 GB per transfer with no disk spooling. The
extended test streams generated bytes through the tunnel and hashes them at the
sink, comparing against the sender's digest.

```bash
TUNNELMATE_LARGE_BYTES=6442450944 \
  TUNNELMATE_BUILD_DIR=$PWD/build .venv/bin/pytest tests/integration -s -k large
```

### Measured — VPS, 6 GiB (6442450944 bytes)

| Mode | Duration | Throughput | Broker peak RSS | Agent peak RSS | SHA-256 |
|---|---:|---:|---:|---:|---|
| open TCP | 11.3 s | 544.2 MiB/s | 9.9 MB | 9.8 MB | matched |
| closed TCP | 14.2 s | 432.9 MiB/s | 10.5 MB | 9.8 MB | matched |

Broker memory is flat for the whole transfer — the same ~10 MB it uses at idle.
That is what bounded buffers plus backpressure buy: transfer size has no
influence on memory. There is no per-transfer disk usage at all, which matters
on a 2 GB disk.

Single transfers are not capped. 6 GiB is the tested figure, not a limit.

### Measured — VPS, 6 GiB aggregate UDP

`TUNNELMATE_UDP_LARGE_BYTES=6442450944` sends ~4.6 million 1400-byte datagrams.
This is total transferred volume, not one enormous datagram.

| Metric | Value |
|---|---|
| Sent | 4,601,751 datagrams / 6.00 GiB |
| Duration | 25.0 s (246.1 MiB/s offered) |
| Broker received | 3,536,730 datagrams / 4.95 GB |
| Dropped by policy | 1,775,694 |
| Broker RSS | 9.7 MB baseline → 11.8 MB peak |

The drops are the point, not a defect: the sender offers datagrams faster than
the tunnel drains them, and the bounded queues shed the excess by documented
policy instead of buffering. Memory grew about 2 MB while moving 6 GiB. An
application that needs no loss should pace itself or use TCP.

## UDP latency and jitter

A UDP tunnel that reaches throughput while adding severe head-of-line latency
is not acceptable, so delay distribution is measured separately.

### Measured — dev, loopback round trip through the tunnel

| Datagram size | samples | lost | p50 | p95 | p99 |
|---:|---:|---:|---:|---:|---:|
| 64 B | 200 | 0 | 0.053 ms | 0.141 ms | 0.656 ms |
| 256 B | 200 | 0 | 0.071 ms | 0.111 ms | 0.182 ms |
| 512 B | 200 | 0 | 0.060 ms | 0.088 ms | 0.101 ms |
| 1200 B | 200 | 0 | 0.065 ms | 0.090 ms | 0.113 ms |
| 1400 B | 199 | 1 | 0.069 ms | 0.098 ms | 0.170 ms |

Continuous 1 kHz telemetry-shaped stream, 2000 datagrams: **0 lost, 0
duplicated, 0 reordered**, inter-arrival jitter 0.331 ms. DTLS carries each
datagram as its own record, so there is no head-of-line blocking between
datagrams — the reason the specification rules out UDP-over-TCP.

## Concurrency and memory

### Measured

| Scenario | Result | Host |
|---|---|---|
| 40 idle tunnels | 224 KiB total growth, **5.6 KiB per idle tunnel** | dev |
| 100 concurrent streams, one tunnel | 0.14 s, 690 conns/s, 15.4 MB broker RSS | dev |
| 256 concurrent streams | 2.08 s, 123 conns/s, 17.4 MB broker RSS | VPS |
| 200 connect/close cycles | no descriptor growth | dev |
| Stalled reader for 6 s | 72 KiB broker growth | dev |
| 128 concurrent UDP flows | 0 lost, 0 misrouted | dev |

An idle tunnel costs about 5.6 KiB, so the 256-tunnel default fits comfortably.
Active TCP streams cost roughly 0.2–0.6 MB each depending on TLS state and
queued bytes; see [operations.md](operations.md) for the memory budget.

## Reproducing

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build --parallel
python3 -m venv .venv && .venv/bin/pip install -e './control[dev]' -e './python-sdk[dev]'
export TUNNELMATE_BUILD_DIR=$PWD/build

tests/load/benchmark.py --bytes 512MiB              # comparison table
.venv/bin/pytest tests/load -s                      # concurrency, UDP latency
TUNNELMATE_LARGE_BYTES=6442450944 \
  .venv/bin/pytest tests/integration -s -k large    # 6 GiB TCP
TUNNELMATE_UDP_LARGE_BYTES=6442450944 \
  .venv/bin/pytest tests/load -s -k aggregate       # 6 GiB UDP
```

Keep the host otherwise idle; these are loopback figures and a busy machine
moves them considerably. Do not compare UDP throughput against TCP throughput —
they are bound by different things.
